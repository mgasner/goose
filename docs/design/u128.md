# u128: a 128-bit unsigned integer type

This note plans adding `u128` to Goose: an unsigned two's-complement
integer twice as wide as `u64`, for hashes and fingerprints, 128-bit IDs
(UUIDs), wide multiply results (`u64 * u64` without losing the high half),
fixed-point accumulators, and bit sets of 128.

Status: plan. Nothing here is implemented.

## 1. Summary

`u128` joins the integer types of spec §3.1. It is a full value type
(locals, fields, array elements, parameters, results, generics), with the
arithmetic, comparison, bitwise and shift operators of §6.1 at unsigned
wrapping semantics (§6.2), checked `as` and unchecked `as!` conversions
to and from every integer and float type (§6.3), integer `match`
(§8.1), and formatting.

Two constraints decide most of the plan:

1. **The C backends cannot all spell a 128-bit integer.** TinyCC, which
   runs every program built without `-o` (`src/jit.h`), has no
   `__int128`. Its sources mention one only in debug-info tables
   (`third_party/tinycc/tccdbg.c:45`), and its parser has no such
   keyword. MSVC has none in C or C++. So the generated C represents
   `u128` as a two-word struct, and every operation on it goes through a
   runtime helper. Under clang and gcc the helpers may use
   `unsigned __int128` internally. The layout stays the struct either
   way, so it is the same in every build.
2. **The compiler's constants are 64 bits wide.** Every integer constant
   travels as `int64_t` plus a flag marking a `u64` above `i64.max`
   (`IntLit::uns`, `Val::uns`, `constuns`, the lexer's `iuns`). The
   range, fit, wrap and fold helpers in `src/ast.h:95-190`, BCE's
   intervals (`src/bce.h:537`) and integer match ranges all compute in
   that model. Phase 1 (§4) leaves the model alone: a `u128` *constant*
   is limited to the `u64` range, and nothing folds or range-tracks at
   `u128`. Phase 2 (§9) widens the constant model if that limit turns
   out to matter.

`i128` is out of scope here, but the design leaves room for it (§10).

## 2. Language design (spec changes)

### 2.1 The type (§3.1)

* Spelled `u128`. It is a new keyword token, like `u64`.
* Size 16 bytes and **alignment 8**: a struct of two `u64` words, low word
  first. Alignment 8 rather than 16 keeps the layout identical whether a
  build uses the native type or the portable one, and it is what `pad`
  (`CodeGen::PadAlign`) reports.
* The default value is 0.
* It is a scalar for §1.1 size classes and §4.1 passing, the same as any
  other integer. Passing it by value costs two words.

### 2.2 Literals and constants (§2, §3.1)

* Integer literals don't change. A literal (or a named constant) adapts
  to `u128` exactly as it adapts to `u64` today: any value from 0 to
  `u64.max` fits. A negative constant does not fit, and the error is the
  existing "doesn't fit" error.
* **Phase 1 limit:** a constant expression *at* `u128` folds only when
  both operands and the result stay in the `u64` range. Anything else is
  a runtime expression. So `let big: u128 = 1 << 100;` compiles, the
  value is computed at run time, and it is correct. What it is not is a
  compile-time constant. A `const`, a `T[k]` size, a match pattern, or
  anything else that *requires* a constant above `u64.max` is a
  compile-time error that names the limit ("u128 constants above u64.max
  are not supported yet").
* The way to write a large value is `(hi as u128) << 64 | lo`. The
  stdlib also gets `u128_from(hi: u64, lo: u64)` (§6).

### 2.3 Implicit conversions (§6.3)

`ImplicitInt` (`src/typecheck.h`, "conversions that can never change a
value") already admits `u8`/`u16`/`u32`/`u64 → u128`: same signedness,
wider. Its rule "unsigned → strictly wider signed" admits nothing new,
because there is no wider signed type. Signed → `u128` is never
implicit. The rule needs no new code, but it must not be skipped by
`IntBits` treating `u128` as 64 bits (§5.1).

### 2.4 Mixed operands and comparisons (§6.1)

* Arithmetic between `u128` and a narrower unsigned type widens to
  `u128`, as any unsigned mix does today.
* Arithmetic between `u128` and a signed type needs an `as` on one side,
  the same as `u64` with a signed type.
* **Comparisons:** today `u64` is "the one unsigned type with no signed
  supertype" (`typecheck_exprs.h:1539-1570`, the `isu64` lambda). A
  comparison between it and a signed operand is allowed when the signed
  side is known non-negative. `u128` gets the same rule. That code
  generalizes from "is `u64`" to "is an unsigned type with no signed
  supertype" (`u64` or `u128`). Comparing `u128` with `u64` is an
  ordinary widening compare.

### 2.5 Operators (§6.1, §6.2)

| Operator | `u128` behaviour |
|---|---|
| `+ - *` | wrap modulo 2¹²⁸. There is no overflow check in any build, as for every unsigned type. |
| `/ %` | unsigned. Division by zero aborts in every build, with the existing message. |
| `& \| ^ ~` | bitwise. |
| `<< >>` | the shift count is masked `& 127`, matching `gs_shl_*`'s masking by width. The count is any integer *except* `u128`. A `u128` count needs `as i64`. |
| unary `-` | an error ("cannot negate a value of unsigned type"), as for `u64`. |
| `== != < <= > >=` | unsigned comparisons. |
| compound `+=` etc., `++ --` | as their binary forms. |

### 2.6 Explicit conversions (§6.3)

* `x as T` from `u128` to a narrower integer is range-checked in debug
  builds and truncates in release builds, as narrowing does today.
* `x as u128` from a signed type checks for a negative value.
* `as!` truncates or reinterprets, as it does today.
* To and from `f32`/`f64`: the conversion rounds to nearest, the same way
  as the `u64` ↔ float paths. A float that is out of range, NaN or
  negative fails the check in `as`, and `as!` saturates or wraps the same
  way `gs_f2iwrap` does for `u64`.

### 2.7 Where `u128` is not allowed

The parser and typechecker give a targeted message for each of these:

* array length storage `T[u128]` and relative-reference widths
  `T&<u128>`. `ParseLengthStorage` (`parser.h:557`) already lists only
  u8–u64 and varint, so it only needs a clearer message;
* index, slice-bound and size positions (`CheckIntAny`). These take
  `as i64`, because a `u128` index can't be a valid offset;
* `for` range bounds (Phase 1; they take `as i64`);
* varint construction stores (§3.6). These already reject `u64`;
* `extern fn` / exported signatures (§7.10, §7.11), until a C ABI is
  decided (§10). A struct `gs_u128` there would surprise C callers who
  expect `unsigned __int128`.

### 2.8 `match` (§8.1)

A `u128` scrutinee matches integer patterns. With the Phase 1 constant
limit, its patterns are in the `u64` range. Exhaustiveness then needs a
wildcard arm unless the arms cover 0 through `u64.max` *and* the
compiler can see that the value is in that range. In practice that means
a wildcard arm is required, and the existing "match on X never matches"
checks (`errors_tc/match_u64_never_matches.goose`) get a `u128` twin.
Codegen emits the existing if-chain using the helper comparisons (§5.4).

### 2.9 Formatting (§3.7 rendering)

`print`, string interpolation and `format` render a `u128` in decimal,
the same as the other integers. Hex goes through the stdlib (§6).

## 3. Runtime representation

The type lives in `src/runtime_inline.h`, next to the `u64` helpers
(lines 313-395):

```c
typedef struct { uint64_t lo, hi; } gs_u128;
```

There are two implementations behind one set of names, chosen with
`#if defined(__SIZEOF_INT128__) && !defined(__TINYC__)`:

* **native**: convert to `unsigned __int128`, operate, convert back. With
  clang and gcc at `-O2`, these conversions compile away.
* **portable**: two-word code for TinyCC and MSVC. Multiplication is
  64×64→128 on 32-bit halves (or `_umul128` on MSVC). Division is
  shift-subtract, with a fast path when both high words are 0 that uses
  a single `u64` divide.

Helpers, all `static inline` and named like the existing ones so that
codegen's `IntSfx` scheme reaches them:

| Group | Helpers |
|---|---|
| construct | `gs_u128_mk(hi, lo)`, `gs_u128_from_u64(v)`, `gs_u128_from_i64(v)` (unchecked, sign-extending, for `as!`) |
| arithmetic | `gs_add_u128`, `gs_sub_u128`, `gs_mul_u128`, `gs_div_u128(a, b, file, line)`, `gs_mod_u128(...)`, `gs_shl_u128(a, n)`, `gs_shr_u128(a, n)` |
| bitwise | `gs_and_u128`, `gs_or_u128`, `gs_xor_u128`, `gs_not_u128` |
| compare | `gs_eq_u128`, `gs_lt_u128`, `gs_le_u128` (codegen swaps operands for `>` and `>=`) |
| narrow | `gs_u128_lo(a)` (`as!` to any narrower type then goes through the existing casts), `gs_rangechk_u128(a, hi, tname, file, line)` (checked `as` to a narrower type, debug only) |
| signed in | `gs_rangechk_i2u128(v, tname, file, line)` (a negative source aborts) |
| float | `gs_u128_to_f64`, `gs_u128_to_f32`, `gs_f2u128chk(d, is_f32, file, line)`, `gs_f2u128wrap(d)` |
| format | `gs_fmt_u128(dst, v)` (decimal: divide by 10¹⁹ to split into `u64` chunks, then `gs_fmt_u64`), `gs_out_u128(v)` |

Release-build macro forms follow the existing `#else` block (lines
364-372): there `gs_rangechk_*` collapses to the truncation.

Equality of structs that contain a `u128` stays `memcmp`
(`codegen_types.h:1191`), because the struct has no padding. A struct
that *contains* a `u128` field is padded to 8 under the new `PadAlign`
entry.

## 4. Phase 1 compiler work, by stage

File and line references are to master at `0a7d222`.

### 4.1 Lexer and parser

* `lexer.h:52`: add `F(T_TU128, "u128")` to the token list.
* `parser.h:561-566` and the type-keyword switch near `ast.h:2164`: map
  `T_TU128` to `IS_U128`.
* `parser.h:557` (`ParseLengthStorage`): `u128` falls into the default
  case. Change the message to say why ("u128 cannot be an array length
  or reference width").
* `parser.h:861`: negating a literal. No change, but add a test showing
  that `-x` with `x: u128` is rejected in typecheck.

### 4.2 `IntStorage` and helpers (`src/ast.h:68-190`)

* Add `IS_U128` **after `IS_U64` and before `IS_VARINT`**, so that
  `IsUnsigned` (`s >= IS_U8 && s <= IS_U64`) only needs its bound moved
  to `IS_U128`. Every array indexed by `IntStorage` gets a new entry
  (`IntStorageName` and any others found in §5.1).
* `IntBits`: return 128 for `IS_U128` explicitly. Its `default: return 64`
  currently covers i64, u64 and varint, and it must not swallow u128.
* `IntRange`: `{0, INT64_MAX}` for `IS_U128`, like `IS_U64`. The comment
  "every user of a u64 range meets that case first" now covers u128 too.
* `FitsIntStorage(v, uns, s)`: `uns` constants fit `IS_U64` **or
  `IS_U128`**.
* `WrapStorage`: identity for `IS_U128`. A Phase 1 constant at `u128` is
  always a u64-range value, so there is nothing to wrap.
* `FoldIntOp`: for `IS_U128`, fold only when both operands are u64-range
  constants and the operation's exact result is in the u64 range. Compute
  it in `uint64_t` with overflow detection; otherwise return false, which
  leaves the expression unfolded. Shifts fold only when `(a << n) >> n == a`
  with `n < 64`.
* `codegen.h:230` `IntSize`: becomes 16 automatically once `IntBits`
  returns 128.

### 4.3 Typechecker

* `typecheck.h` `ImplicitInt`: no logic change (§2.3). Add a unit test
  that each unsigned type widens and no signed type does.
* `typecheck_exprs.h:1500-1570` (operand unification):
  * the `lv.uns || rv.uns` branch (1509-1516) returns `IS_U64` for an
    unsized constant above `i64.max`. When the other operand is `u128`,
    the constant adapts to `u128` instead;
  * generalize `isu64` to `IsTopUnsigned(s)` (`IS_U64 || IS_U128`). When
    *both* sides are top-unsigned, the ordinary `ImplicitInt` path above
    already unified them.
* `typecheck_exprs.h:1144-1193` (constant adaptation, `RecordLitAdapt`):
  the `t->intstorage != IS_U64 && != IS_VARINT` test (1171) gets
  `IS_U128` too.
* `typecheck_exprs.h:1474`: `out.uns = s == IS_U64 && res < 0`. At `u128`
  a folded result is never `uns` in Phase 1, because folding refused it.
* `typecheck_exprs.h:1833`: an `lv.uns` constant defaults to `u64`
  (unchanged).
* `typecheck_exprs.h:1913-1926` (negation): add `IS_U128` to the
  unsigned rejection (it is already reached through `IsUnsigned`).
* Constant-required positions (`const`, sizes, patterns, defaults that
  must be constant): when the value would have to exceed `u64.max`, give
  the Phase 1 error from §2.2. In Phase 1 such a value can only arise
  from an unfolded expression, so it is enough to make "not a constant"
  in these positions mention the limit when the type is `u128`.
* `CheckIntAny` (indices, slice bounds, sizes, shift counts, `for`
  bounds): reject `u128` with "convert it with `as i64`".
* §3.6 varint store check: the same 1171 test is the varint rejection
  ("every integer type embeds except u64"); adding `IS_U128` there covers
  it.
* `extern fn` / export signature checks: reject `u128` (§2.7).
* Integer match (`typecheck.h:682`, `typecheck_flow.h`): patterns at a
  `u128` scrutinee use the existing `u64`-bits path. Exhaustiveness
  treats the domain as larger than any finite pattern set, so a wildcard
  is required.
* Flow facts (`nonneg`, `litlo`/`lithi`): a `u128` value is always
  non-negative. Its `litlo`/`lithi` stay inside the u64 range, or the
  fact is dropped.

### 4.4 Bounds-check elimination and the optimizer

* `bce.h` `Ival` is `int64_t lo, hi`. For a `u128` term, return "no
  interval" (`ok = false`). Indices can't be `u128` (§2.7), so BCE loses
  nothing.
* `optimize.h` (seven `uns` sites): treat `u128` like an unknown, so
  there are no folding or strength reductions at `u128` in Phase 1. Audit
  each `IntBits`/`IntRange` use.
* `optimize_tre.h` / `optimize_basecase.h`: no expected changes, but
  audit their integer switches.

### 4.5 Codegen

`IntCT` (`codegen_types.h:201`) returns `"gs_u128"` and `IntSfx` (215)
returns `"u128"`. Both now end in `default:` branches that would quietly
emit `int64_t`/`i64`, so give them explicit cases.

The rest of codegen assumes an integer is a C arithmetic type. These are
the sites that emit a raw C operator, cast or constant for an integer.
Each needs a `u128` branch that calls the helpers instead:

Test it with a `struct { a: u128, b: u128 }`.

## 5. Audits

These have to be done by reading, not grepping for "u64":

1. **Every `switch` over `IntStorage`** (about 109 `case IS_*`/`IntStorage`
   sites across `src/*.h`). Most fall through a `default:` that means
   "i64 or u64 or varint". Each one gets an explicit `IS_U128` case or an
   `assert`. Building with `-Wswitch-enum` once to list them is the
   fastest way.
2. **Every `IntBits(s) == 64` or `IntSize(s) == 8` test**, e.g.
   `codegen_construct.h:21` (`if (IntSize(ls) == 8) return;` followed by
   `1ull << (IntSize(ls) * 8)`, which is UB at 128). With `u128` these
   become "≥ 64" tests or need explicit exclusion.
3. **Every place that compares `intstorage == IS_U64`** (about 20 sites,
   listed by `grep -n IS_U64 src/*.h`). Decide for each one whether it
   means "the widest unsigned type", which then includes `u128`, or
   "exactly u64".
4. **C operators applied to an integer value**, beyond the table in §4.5:
   `grep -n '" < "\|" == "\|" & "\|"(int64_t)"' src/codegen*.h` and check
   each result's operand types.

* `hash(x: u128) -> u64`: `hash_combine(hash_mix(lo), hash_mix(hi))`, in
  the scalar overload set at lines 100-110.
* `popcount`, `clz`, `ctz` overloads for `u128`, written on the two
  words.
* `u128_from(hi: u64, lo: u64) -> u128`, `u128_hi(x) -> u64`,
  `u128_lo(x) -> u64`.
* `mul_wide(a: u64, b: u64) -> u128`. This is the main motivating case,
  and with the native helper it compiles to a single `mul`.
* `parse_u128(s: u8[:], base: i64 = 10) -> u128, bool` next to
  `parse_int` (673).
* `fmt_hex(x: u128)` / zero-padded hex, for UUID-style output, wherever
  the existing hex formatting lives.
* `binary.goose`: `read_u128_le`/`_be` and the writers, alongside the
  `u64` checked readers.
* `rng`: optionally `next_u128`.

  `unsigned __int128` over random inputs. This catches portable-path

## 9. Phase 2 (optional): 128-bit constants

Do this only if Phase 1's limit bites, for example when `const MASK: u128
= …` or match patterns above `u64.max` are wanted. It replaces "`int64_t`
plus `uns`" with a portable 128-bit constant type in the compiler. The
compiler builds with MSVC too, so this is a small `struct Int128` class
with the arithmetic and not `__int128`.

The work touches the lexer (128-bit decimal and hex literal accumulation),
`IntLit`/`Val`/`constval` storage, `IntRange`/`FitsIntStorage`/
`WrapStorage`/`FoldIntOp`, the approximately 75 `uns` sites,
`litlo`/`lithi` flow facts, BCE `Ival`, match exhaustiveness intervals,
`dump.h`, and `IntLit::CgX` (`gs_u128_mk(hi, lo)`). It would also
retire the `uns` flag in favour of the wider type, which simplifies the
existing `u64` code. The estimate is 1,000-2,000 lines, with most of the
risk in typecheck regressions.

## 10. Open questions

1. **`i128`.** With the helpers in place, `i128` costs about another
   30%: signed division and Euclidean `%` (§6.2), overflow-checked
   `+ - *` in debug builds, sign-aware `as`, and the comparison rules.
   Should we do it together with `u128` or later?
2. **C ABI.** Should `extern fn` accept `u128` as `unsigned __int128`
   where the C compiler has it? Then `gs_u128` would need to be the
   native type in those builds and give up the uniform layout. Phase 1
   keeps it out of C signatures.
3. **Alignment.** Phase 1 uses 8. If a future native-only build wants 16
   for performance, layouts would differ between JIT and AOT builds.
   Nothing serializes raw struct memory across those builds today, but
   `design/serialization.md` should be checked.
4. **Literal syntax.** Phase 2 could add a suffix or rely on adaptation
   alone. Adaptation alone matches the rest of the language.
5. **goose_in_goose.** Should the self-hosted checker track the type
   list?

## 11. Milestones

Each step is a separately reviewable commit or PR, and the test suite
passes after each one:

1. **Runtime helpers and their C unit test.** No compiler change.
2. **Type plumbing:** token, `IS_U128`, `IntBits`/`IntCT`/`IntSfx`/
   `PadAlign`, the `IntStorage` switch audit (§5.1-5.3), and
   typecheck acceptance with the §2.7 rejections. Declarations, copies
   and passing work.
3. **Operators:** the §4.5 codegen table, the compare and unify rules
   (§2.4), and fold refusal. The arithmetic, compare and match tests
   pass under both the C compiler and TinyCC.
4. **Conversions and formatting:** `AsCast`, float conversion, render,
   and the abort tests.
5. **Stdlib, spec and docs, the VS Code grammar.**
6. **(Optional) Phase 2 constants.**

Rough size of steps 1-5: 1,500-2,500 lines including tests.
